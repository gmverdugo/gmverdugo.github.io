Honestidad técnica primero — el cluster NO está en crisis

Estado green, 0 rechazos en thread pools de write/search, 0 full GC (old) y disco hot al 45–56%. Lo que existe es una ineficiencia estructural masiva: over-sharding a 3,9× del límite oficial. Consume heap y CPU, infla el cluster state, ralentiza búsquedas y elimina el headroom para crecer o recuperarse de una falla. La solución es software y arquitectura, sin agregar hardware.

⛬ Diagnóstico

Causa raíz

Por qué los nodos HOT están sufriendo — ordenado por severidad

#1 · Over-sharding severo en HOT

Dominante

Presupuesto hot: 47 GB heap × 20 = ~940 shards máx. recomendados. Realidad: ~3.650 shards ≈ 78/GB → 3,9× sobre el límite. Cada shard tiene costo fijo de heap y cluster state sin importar su tamaño. Con 0,74 GB promedio pagás overhead de 2.256 shards para datos que cabrían en ~56 shards de 30 GB.

#2 · Rollover por edad en streams de bajo volumen

Alto

Rollan por max_age (1d/7d/15d/30d) mucho antes de max_primary_shard_size=50gb, generando backing indices diminutos o vacíos:

  • ctm_alerts_index → 62 shards, ~0 GB (rollover diario)
  • metrics-endpoint.* (×6) → 39–48 shards, 0 GB vacíos
  • endpoint.events.network-linux → 54 shards, 2,2 GB
  • logs-system.*-controlm (×8) → 32 shards, <1 GB

#3 · Faltan fases cold (sin migración fuera de hot)

Alto

Muchas políticas son hot-only → delete sin migración (endpoint, cloud_security_posture, casi todas las apm, synthetics, logs@lifecycle, metrics@lifecycle). Datos como process-windows (178 GB) o vulnerabilities (44 GB / 180d) ocupan el recurso más caro toda su vida. Nota de topología: este cluster NO tiene tier warm (3 hot · 3 cold · 3 frozen), así que la migración correcta es hot → cold (searchable snapshot) → frozen/delete; una fase warm quedaría en error por falta de nodos.

#4 · Explosión de segmentos sin force-merge

Medio

~28.500 segmentos por nodo hot (~23/shard). Sin force-merge al salir de hot, cada query recorre miles de segmentos extra → CPU de búsqueda y overhead de heap innecesarios.

#5 · Sprawl de configuración: 91 políticas ILM

Medio

Duplicados evidentes (180-days-default ≡ 180-days@lifecycle, etc.) y políticas one-off. No consume runtime directamente, pero hace ingobernable el ciclo de vida y perpetúa las causas #2 y #3.

◎ Mitigación

Estrategias — el "por qué" y el "cómo"

Mejoras específicas para Elasticsearch 9.x alineadas a las best practices oficiales
A · Sharding

Frenar la generación de shards diminutos

El tamaño no se arregla cambiando number_of_shards (ya hay 1 primario): se arregla rollando menos seguido. Subí max_age y dejá que mande el tamaño.

PUT _ilm/policy/logs-lowvolume-standard
{
  "policy":{ "phases":{
    "hot":{ "actions":{ "rollover":{
      "max_primary_shard_size":"50gb",
      "max_age":"30d" // antes 1d/7d
    }}},
    // sin tier warm: force-merge + searchable snapshot en COLD
    "cold":{ "min_age":"10d",
      "actions":{ "forcemerge":{ "max_num_segments":1 },
        "searchable_snapshot":{ "snapshot_repository":"found-snapshots" }}}
  }}
}

Por qué: Elastic recomienda shards de 10–50 GB para logs/métricas. Subir max_age reduce backing indices sin tocar el tope de 50 GB.

B · Data tiers

Sacar datos de HOT rápido

Como el cluster no tiene tier warm, toda política de logs/métricas debe migrar a cold lo antes posible (con force-merge + searchable snapshot) y delete según retención. Esto solo libera el grueso de los 1.673 GB y miles de shards del tier hot.

Por qué: los datos read-only deben migrar al tier más barato disponible. HOT se reserva para indexación activa y búsquedas recientes.

C · Force-merge

1 segmento antes de cold

Force-merge a 1 segmento en índices read-only antes de moverlos a cold. Sin tier warm, la acción va en la fase cold (o hot tras rollover).

"cold":{ "min_age":"10d",
  "actions":{ "forcemerge":{
    "max_num_segments":1 }}}

Por qué: menos heap, búsquedas más rápidas, snapshots más chicos. Nunca force-merge sobre índices que aún reciben escrituras.

D · Ingesta

Refresh interval — gran palanca de CPU

El default de 1s fuerza creación constante de segmentos y merges. Para logs/métricas, 30s reduce drásticamente la presión.

PUT _component_template/logs-settings
{ "template":{ "settings":{
  "index.refresh_interval":"30s" }}}

Por qué: logs/métricas no necesitan visibilidad sub-segundo. Bulk recomendado: 5–15 MB por request.

E · Limpieza

Decomisionar streams vacíos

Los metrics-endpoint.* a 0 GB con 39–48 shards: si no se consultan, desactivá esas integraciones en Fleet. Cada stream eliminado borra decenas de shards del cluster state.

Por qué: no recolectar telemetría sin un caso de uso real.

F+G · Gobierno + Query

Consolidar ILM y optimizar búsquedas

Reducir 91 → ~8–10 políticas canónicas por SLA. En queries: usar filter context (cacheable), rango temporal siempre presente, index.codec: best_compression en cold, evitar wildcards líderes y scripts en hot path.

Por qué: filter context es cacheable; los rangos temporales permiten a los data tiers podar shards.

G · Query · T9

filter context — guía de migración (app-side)

Las condiciones binarias (¿coincide sí/no?) van a filter; en must dejá solo las cláusulas que aportan relevancia (match, multi_match). El filter context no calcula score y es cacheable en el node query cache → menos CPU y búsquedas repetidas más rápidas.

// ANTES — todo en must (calcula score de term/range, no cachea)
{ "query":{ "bool":{ "must":[
  { "match":{ "message":"error timeout" } },
  { "term":{ "service.name":"checkout" } },
  { "range":{ "@timestamp":{ "gte":"now-15m" } } }
]}}}
// DESPUÉS — binarias a filter (sin score, cacheable, poda shards por tier)
{ "query":{ "bool":{
  "must":[ { "match":{ "message":"error timeout" } } ],
  "filter":[
    { "term":{ "service.name":"checkout" } },
    { "range":{ "@timestamp":{ "gte":"now-15m" } } }
  ]
}}}

Dónde lo controla MELI: Kibana ya manda los filtros de la barra (KQL) como filter; el ahorro real está en DSL crudo de dashboards/Lens, reglas de detección de Security, transforms, watchers y código de búsqueda de las apps. Regla de oro: incluir SIEMPRE el rango de @timestamp en filter → el can-match descarta shards fuera de ventana antes de buscar (clave con cold/frozen).

G · Codec · T9

best_compression (ZSTD) — palanca de disco

index.codec: best_compression usa ZSTD: ~28% menos disco con throughput de indexación similar. El único costo es get-by-id 10–33% más lento — irrelevante para logs/métricas/telemetría (consultan por búsqueda y agregación, no por id).

// STATIC: solo aplica a índices NUEVOS → vía slot @custom (rollover)
PUT _component_template/logs-elastic-cloud-logs@custom
{ "template":{ "settings":{
    "index.codec":"best_compression" }}}

Hallazgo al validar en vivo (2026-06-10): 2.378 de 3.040 índices (78%) YA usan best_compression — lo setea Elastic/Fleet por default en sus integraciones. O sea, la palanca ya está tirada donde más importa. Decisión — no forzarla global: el cuello de botella es shards/heap, no disco; el codec no reduce ni un shard, e ILM no lo cambia por fase. Para el ~22% restante (custom/sistema en LZ4) es opcional y solo vale si aparece presión de disco. Confirmado: no había nada que hacer acá.

🟡 endpoint.events.process — command lines

Seguridad

17M docs con process.command_line / args no indexados → threat hunting ciego por command line. Aunque es solo 0,7%, el impacto de seguridad es alto (es uno de los campos más usados en detección).

Fix: via logs-endpoint.events.process@custom, mapear command_line/args como wildcard — el tipo que Elastic recomienda para strings largos: buscable, sin ignore_above.

Método
